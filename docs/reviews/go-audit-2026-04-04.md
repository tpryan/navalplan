# Go Code Audit — 2026-04-04

## Scope

Full audit of both Go modules in the repository:

1. `code/app/backend/` — HTTP REST API server (~47 source files)
2. `code/services/researcher/` — AI agent orchestration microservice (~17 source files)

Approximately 5,000 lines of production code reviewed (excluding tests and vendor directories).

---

## Summary

The backend is well-structured for a standard Go HTTP server. The handler/datastore/models separation is clear, and the semaphore pattern for rate-limiting concurrent research is a good call. The main concerns are a security-relevant unchecked error in auth, HTTP calls without timeouts (which can cause goroutine accumulation), a race condition in the rate limiter, and several places where errors are silently swallowed. There is also a consistent pattern of too much business logic living in handler functions.

---

## Issues by Severity

### Critical — Security / Stability

**1. `rand.Read()` error not checked — `server/auth.go:131, 157`**

Both calls to generate random bytes for session tokens and OAuth state values ignore the return error.

```go
b := make([]byte, 16)
rand.Read(b) // error ignored
state := base64.URLEncoding.EncodeToString(b)
```

If `rand.Read()` fails (rare but possible), the byte slice will be zero-filled, producing weak/predictable tokens. For OAuth state this could enable CSRF; for session tokens it could enable session fixation.

Fix:
```go
b := make([]byte, 16)
if _, err := rand.Read(b); err != nil {
    http.Error(w, "Internal Server Error", http.StatusInternalServerError)
    return
}
```

---

**2. HTTP calls without timeouts — `server/handlers/research.go:74, 101` and `server/auth.go:143`**

Three locations use `http.Get()` directly with no timeout:

- `getStaticMap()` — calls Google Static Maps API
- `GeocodeFacility()` — calls Google Geocoding API
- `getUserDataFromGoogle()` — calls Google userinfo endpoint

If Google is slow or unresponsive, these goroutines hang indefinitely. Under load this accumulates connections and exhausts the process.

Fix: Use a client with a timeout, or pass a context:
```go
ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
req, err := http.NewRequestWithContext(ctx, http.MethodGet, endpoint, nil)
resp, err := http.DefaultClient.Do(req)
```

### High — Correctness / Race Conditions

**3. Race condition in rate limiter — `server/middleware.go`**

`sync.Map` prevents concurrent map-level races, but the entry struct's fields (`count`, `lastSeen`) are mutated without synchronization after being loaded from the map. Multiple goroutines serving concurrent requests for the same client IP will race on these fields.

Fix: Add a mutex to the entry struct:
```go
type rateLimitEntry struct {
    mu       sync.Mutex
    count    int
    lastSeen time.Time
}
```

---

**4. Errors silently swallowed in `admin.go` — `server/handlers/admin.go:37-38`**

All three database calls in the admin list handler use `_` to discard errors:

```go
people, _ := h.DB.ListPeople(r.Context(), limit, offset)
totalPeople, _ := h.DB.CountPeople(r.Context())
invites, _ := h.DB.ListInvitations(r.Context())
```

On database failure, the handler returns an empty/incomplete JSON response with status 200 — no indication of failure.

Fix: Check errors and return 500.

---

**5. Agent session creation errors not handled — `research.go:197`, `guide.go:204`, `recommendation.go:239`, `discovery.go:194`**

All four agent call sites log the session creation error but then continue and call `/api/run` anyway:

```go
respSession, err := client.Post(createSessionURL, ...)
if err != nil {
    slog.ErrorContext(ctx, "Failed to create agent session", "error", err)
} else if respSession != nil {
    respSession.Body.Close()
}
// execution continues to /api/run — which will fail differently
```

This masks the root cause and produces confusing cascading errors in logs.

Fix: Return early on session creation failure.

---

**6. `context.Background()` in async goroutines — `research.go:176`, `research.go:404`, `guide.go`, `recommendation.go`, `discovery.go`**

All background goroutines create a fresh `context.Background()` rather than deriving from the request context. This loses:
- Request cancellation signals
- Any trace/span IDs injected by middleware
- Timeout propagation

For long-running operations (research, guide generation) this means they continue running even if the client disconnects or the request is cancelled.

Fix: Either pass a server-scoped context with a generous timeout, or use `r.Context()` with the understanding that it will be cancelled when the HTTP response is sent (for fire-and-forget operations, derive from a long-lived server context).

### Medium — Reliability / Observability

**7. Missing goroutine cancellation for year-long discovery mining — `discovery.go:92-98`**

The full-year mining cycle launches 12 sequential `performDiscoveryMining()` calls in a goroutine with no timeout or cancellation:

```go
go func() {
    for m := 1; m <= 12; m++ {
        h.performDiscoveryMining(m)
    }
}()
```

If the agent is unresponsive on any month, the goroutine is stuck and never finishes, quietly leaking.

Fix: Pass a context with timeout to each mining call.

---

**8. SSE channel close panic risk — `recommendation.go:137-173`**

The defer in `StreamRecommendations` closes the session channel:

```go
defer func() {
    muRecStreams.Lock()
    delete(recStreams, sessionID)
    close(ch)
    muRecStreams.Unlock()
}()
```

If the channel is somehow closed by another path, the `close(ch)` panics. Low probability with current flow, but should be protected with `sync.Once`.

---

**9. `RadiusMiles` field never set — `recommendation.go`**

`VoyageRecommendation.RadiusMiles` is defined in the model and stored in the database, but is never assigned a value when creating recommendations. It will always be `0.0`.

Fix: Compute from `SearchRadius` and `SearchRadiusUnit` when building the recommendation.

---

**10. Global mutable SSE stream state — `recommendation.go:120-123`**

```go
var (
    muRecStreams sync.RWMutex
    recStreams   = make(map[string]chan models.VoyageRecommendation)
)
```

Package-level global state makes this hard to test in isolation and problematic for horizontal scaling (two instances can't share the same in-memory map). Fine for a single-instance deployment on Cloud Run; worth noting if scaling plans change.

Fix: Move to the `Handler` struct.

---

**11. No structured error format across handlers**

Some handlers return descriptive error bodies:
```go
http.Error(w, "Voyage not found", http.StatusNotFound)
```

Others return generic ones:
```go
http.Error(w, "Internal Server Error", http.StatusInternalServerError)
```

There is no consistent JSON error envelope. This makes client-side error handling inconsistent.

Fix: Define a shared error response helper, e.g.:
```go
func writeError(w http.ResponseWriter, code int, msg string) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(code)
    json.NewEncoder(w).Encode(map[string]string{"error": msg})
}
```

---

**12. Business logic embedded directly in HTTP handlers**

Functions like `performStopResearchLogic()`, `performRecommendationGeneration()`, `performGuideResearch()`, and `performDiscoveryMining()` are 80-150 lines each, mixing:
- External HTTP calls to the AI agent
- JSON parsing and transformation
- Database writes
- Error logging

This makes them difficult to unit test and violates single responsibility. Extracting to a service layer would allow the handlers to remain thin coordinators.

---

### Low — Minor / Maintenance

**13. Nil pointer dereference risk — `guide.go:213-219`**

```go
if voyage.PreciseLocation != nil && *voyage.PreciseLocation != "" {
    locDetail = fmt.Sprintf("...", locName, *voyage.Latitude, *voyage.Longitude)
}
```

`voyage.Latitude` and `voyage.Longitude` are dereferenced without nil checks. If `PreciseLocation` is set but lat/lng are nil for any reason, this panics.

---

**14. Overly complex response format detection — `recommendation.go:280-324`**

The streaming response parser reads the first byte to detect whether the format is a JSON array or NDJSON, then handles two separate parsing paths. The first `Read()` error is discarded:

```go
n, _ := resp.Body.Read(firstByte)
```

This is fragile. A cleaner approach is to require the agent to always return a single format.

---

**15. `getStaticMap()` and `GeocodeFacility()` are package-level functions, not methods**

`GeocodeFacility()` is exported and standalone but has no test coverage and is only called from one place. It could be a private helper or moved to a utility package for clearer ownership.

## Researcher Service (`code/services/researcher/`)

**16. No timeout on agent/model initialization at startup**

Agent and model creation during server startup uses `context.Background()` with no timeout. If the Gemini API is unresponsive, server startup hangs indefinitely with no error logged until the process is killed externally.

Fix: Add a startup timeout context (e.g., 30 seconds).

---

**17. Provider `Close()` errors are logged but not acted on**

The server's `Close()` method calls each provider's `Close()`. Errors are logged but resources may still leak. This is acceptable for a shutdown path but worth noting.

## What Was NOT Found

- No SQL injection risks — all queries use parameterized `pgx` calls
- No exported symbols that are clearly dead (all appear used or are part of the public handler API)
- No circular imports
- The semaphore pattern in `ResearchSem` (capacity-10 channel) correctly limits concurrent research goroutines
- The `sync.Map` pattern for SSE streams is sound at the map access level (the race is only within individual entries)
